# commit: 변경사항 분석 후 컨벤션 커밋

현재 저장소의 변경사항을 분석해 의미 단위로 나누고, 그 저장소의 컨벤션에 맞는 커밋 메시지를 작성해 사용자 승인 후 커밋한다.

## 워크플로우

### Step 1: 현재 상태 파악

다음을 병렬로 실행한다:

- `git status` — 추적되지 않은 파일 포함 전체 변경 파일 목록 확인 (`-uall`은 대형 저장소에서 메모리 문제를 일으킬 수 있으니 쓰지 않는다)
- `git diff` 및 `git diff --staged` — staged/unstaged 변경 내용 확인
- `git log --oneline -20` — 이 저장소가 실제로 쓰는 커밋 메시지 컨벤션 확인 (prefix 스타일, 언어, 길이 등)

저장소 루트에 `AGENTS.md` 또는 `CLAUDE.md`가 있으면 커밋 관련 지침(메시지 형식, 훅, 금지 사항 등)이 있는지 확인하고 있으면 그것을 이 스킬보다 우선한다.

변경사항이 전혀 없으면(추적 안 된 파일도 없음) 그 사실을 알리고 종료한다.

### Step 2: 논리적 단위로 분류

변경된 파일과 diff 내용을 보고, 서로 관련 없는 변경을 하나의 커밋에 뭉치지 않도록 묶음을 나눈다.

- 같은 목적(같은 버그 수정, 같은 기능 추가)으로 여러 파일이 바뀌었으면 하나의 묶음으로 취급한다.
- 목적이 다른 변경(예: 버그 수정 + 새 기능 추가, 리팩터링 + 오타 수정)이 섞여 있으면 별도 커밋으로 분리할지 사용자에게 제안한다.
- 분류가 애매하거나 사용자가 "그냥 한 번에 커밋해줘"라고 하면 하나의 커밋으로 묶어도 된다. 이 스킬의 목적은 무조건 잘게 쪼개는 것이 아니라, 커밋 히스토리가 나중에 봐도 이해되게 만드는 것이다.

분류 결과(몇 개의 커밋으로 나눌지, 각각 어떤 파일이 포함되는지)를 간단히 사용자에게 보여준다.

### Step 3: 커밋 메시지 작성

기본 형식은 Conventional Commits 스타일의 한국어 메시지다:

```
type: 요약
```

- `type`은 변경 성격에 맞게 선택한다: `feat`(새 기능), `fix`(버그 수정), `refactor`(동작 변경 없는 구조 개선), `chore`(빌드/설정/잡무), `docs`(문서), `test`(테스트), `style`(포맷팅) 등.
- 요약은 "무엇을 했는가"보다 "왜 했는가/무엇이 달라지는가"에 초점을 맞춘 한 줄로 쓴다.
- 필요하면 본문을 추가해 배경이나 이유를 설명한다. 코드만 봐도 알 수 있는 내용(무엇을 바꿨는지)은 반복하지 않는다.

**Step 1에서 확인한 이 저장소의 실제 커밋 로그가 이 형식과 다르면(영어 사용, 다른 prefix, 이모지 등) 이 스킬의 기본 형식보다 저장소의 실제 컨벤션을 따른다.** 이 스킬은 컨벤션이 없는 저장소를 위한 기본값을 제공하는 것이지, 기존 컨벤션을 덮어쓰기 위한 것이 아니다.

여러 커밋으로 나누기로 했다면 각 커밋의 메시지를 모두 작성해 사용자에게 제시한다.

### Step 4: 사용자 승인 후 커밋

작성한 커밋 메시지(들)를 사용자에게 보여주고 승인을 받는다. 승인 전에는 어떤 git 명령도 실행하지 않는다.

승인받으면 각 논리 단위마다 다음을 반복한다:

1. 해당 묶음에 속한 파일만 `git add <파일...>`로 스테이징한다. `git add -A`나 `git add .`는 쓰지 않는다 — 관련 없는 파일이나 `.env`, 자격증명 파일이 실수로 포함될 수 있다.
2. 커밋 메시지는 항상 HEREDOC으로 전달해 줄바꿈과 특수문자가 깨지지 않게 한다:
   ```
   git commit -m "$(cat <<'EOF'
   fix: 로그인 시 토큰 만료 검증 누락 수정

   EOF
   )"
   ```
3. 커밋 후 `git status`로 정상적으로 반영됐는지 확인한다.

여러 커밋을 순서대로 만들 때는 각 커밋이 끝날 때마다 진행 상황을 짧게 알린다.

## 안전 규칙

- `--no-verify`, `--amend`, `-c commit.gpgsign=false` 등은 사용자가 명시적으로 요청하지 않는 한 쓰지 않는다.
- pre-commit 훅이 실패하면 원인을 고치고 **새 커밋**을 만든다. 실패한 커밋은 실제로 생성되지 않았으므로 `--amend`는 직전의 다른 커밋을 건드리게 되어 위험하다.
- `.env`, `credentials.json`, 각종 키 파일 등 시크릿으로 보이는 파일이 변경 목록에 있으면 커밋 전에 사용자에게 알리고 포함 여부를 확인한다.
- push는 사용자가 요청하지 않는 한 하지 않는다. 커밋만으로 작업을 마친다.
- 커밋 메시지는 이 스킬(또는 이전 대화)에서 실제로 분석한 변경 내용만 반영한다. 확인하지 않은 내용을 지어내지 않는다.
